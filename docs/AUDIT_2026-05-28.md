### A1. [medium] Distance-1 SymSpell index over 96k words also runs unbounded relative to the heap budget
- **File:** `ime/nlp/latin/LatinLanguageProvider.kt`  ·  **fix risk:** low
- **Verified:** Verified against the real code AND the real dictionary assets. from() (LatinLanguageProvider.kt:795-821) builds correctionWords with only two filters: word.length >= 2 and frequency >= CorrectionIndexMinFrequency(96/255), capped at MaxCorrectionIndexWords=96_000. I parsed the actual shipped English corpus (data.json + en_supplemental.json, 520,837 distinct normalized words) and found 94,934 words clear the length>=2 AND freq>=96 filter — i.e. the 96,000 cap is essentially BINDING, not a comfortable non-binding ceiling. The frequency floor prunes the 520k tail but still leaves ~95k words. Avg qualifying length is 8.14 and the sum of lengths is 772,605, so SymSpellIndex.build (SymSpellIndex.kt:48-71) generates ~772K distance-1 delete-forms — matching the finding's ~770K estimate. Each delete key costs a String + HashMap.Node, and build holds the transient HashMap<String,MutableSet<String>> builder AND the frozen HashMap<String,Array<String>> simultaneously (lines 58/66-69), so the build-time spike is roughly double the resident size — a tens-of-MB resident / ~100MB-class transient allocation on an Android IME heap that is typically capped well under 256MB. Confirmed NO guard exists: grep found no OutOfMemory/freeMemory/maxHeap/Runtime reference anywhere in ime/nlp, and the lazy block (lines 697-719) has no try/catch or budget check. The missing per-word length ceiling is real — distance-2 filters word.length in 3..MaxDistanceTwoCorrectionWordLength(12) with a tighter 24_000 cap (lines 789-791, 811-819), while distance-1 has neither; I confirmed 20-23 char words (internationalization freq 133, pricewaterhousecoopers freq 128) actually survive the freq floor and enter the distance-1 pool. Both indexes are independent `by lazy` fields (symSpellIndex line 697, symSpellDistance2Index line 726) and can be resident at once. Where I diverge from the finding: distance-1 delete-forms grow LINEARLY in word length (generateDeletes returns exactly L forms at distance 1, SymSpellIndex.kt:77-83), so the missing length cap inflates the index only marginally vs the dominant ~95k-word count — long words are a small fraction. The real driver is the word COUNT, not the absence of a length cap. The dominant heap risk (the distance-2 combinatorial index) is Finding 1; this distance-1 index is a meaningful but lower-magnitude compounding contributor. Net: real resource issue, but the wording 'unbounded' overstates it (it is bounded by a binding 96k cap, just set high) — medium, not high.
- **Fix:** Two surgical changes in LatinDictionarySnapshot.companion (LatinLanguageProvider.kt). (1) Lower MaxCorrectionIndexWords from 96_000 toward ~40_000-60_000 — verified the corpus has ~95k qualifying words so 96_000 is effectively no cap; 40_000 keeps the most common words (the long frequency tail near freq 96 contributes little correction value but ~half the delete-forms). (2) Add an upper length ceiling to the distance-1 filter at line 798, mirroring distance-2: change `word.length >= 2 && frequency >= CorrectionIndexMinFrequency` to `word.length in 2..MaxCorrectionWordLength && frequency >= CorrectionIndexMinFrequency` with a new const MaxCorrectionWordLength (e.g. 16-18 — high enough to keep real words like 'internationalization' is optional; 16 drops only the 20+ char tail). (3) Optionally wrap the SymSpellIndex.build calls in both lazy blocks (lines 706 and 735) in a runCatching that degrades to an empty index on OutOfMemoryError, shared with Finding 1's guard, so a low-memory device falls back to no-correction rather than crashing the IME process. (1) and (2) are the load-bearing changes; (3) is the graceful-degradation hardening the finding requests.

### A2. [medium] Staged init exceptions are captured but never surfaced — fatal app-init failures are silently swallowed
- **File:** `FlorisApplication.kt`  ·  **fix risk:** low
- **Verified:** Verified by reading all four cited files in full plus a repo-wide grep. FlorisApplication.onCreate (lines 100-159) wraps the synchronous init body in `try { ... } catch (e: Exception) { CrashUtility.stageException(e); return }`. CrashUtility.stageException (CrashUtility.kt:159-163) only writes the throwable into the static `stagedException` field. The sole consumer, handleStagedButUnhandledExceptions (CrashUtility.kt:166-173), is dead code — grep across the whole repo finds it defined but never called (other matches are in generated baseline-prof.txt and a fastlane changelog, no call sites). FlorisAppActivity.onCreate (read in full, lines 100-170) has zero CrashUtility references, so the staged exception is never drained when Settings opens. CrashDialogActivity.onCreate:74 reads only CrashUtility.getUnhandledStacktraces(this) (file-based stacktraces in the noBackupFilesDir/unhandled_stacktraces dir) and never reads the in-memory staged exception. The catch block has no flogError, no file write, no notification — a synchronous init failure (e.g. inside CrashUtility.install or a registry setActive) is captured then orphaned with no diagnostic. Two corrections to the finding's framing that lower severity: (1) the real prefs load runs inside scope.launch in init() (lines 163-170); coroutine failures there are NOT caught by onCreate's try/catch, so the catch primarily guards the rare synchronous registry/install/emoji-init steps, not the async prefs bootstrap; (2) the user-facing impact is the Settings app surface, and only on those rare synchronous failures — not a routine blank-keyboard scenario. The defect (orphaned exception, no log) is real, so confirmed=true, but high overstates frequency/impact; medium is honest.
- **Fix:** Two-part. (1) Make the catch non-silent: in FlorisApplication.kt:155-158 add a log line before staging, e.g. `} catch (e: Exception) { flogError { "FlorisApplication.onCreate init failed: $e" }; CrashUtility.stageException(e); return }` (flogError is already imported at line 48). This guarantees the exception appears in logcat/Flog even on release-debug builds. (2) Drain the staged exception so it routes through the real UncaughtExceptionHandler (writes a .stacktrace file + posts the crash notification): call CrashUtility.handleStagedButUnhandledExceptions() once at the top of FlorisAppActivity.onCreate, right after super.onCreate(savedInstanceState) (line 105). Caveat: handleStagedButUnhandledExceptions invokes UncaughtExceptionHandler.uncaughtException, which calls Process.killProcess/exitProcess(10) — that intentionally kills the Settings process to surface the crash, matching upstream FlorisBoard behavior. If killing the freshly-opened Settings activity is undesirable, use only part (1) plus a direct stacktrace-file write in the catch instead of the full handler. Lowest-risk minimal change is part (1) alone, which removes the invisibility without any process-kill side effect.

### A3. [low] Restore data-integrity failures use printStackTrace() instead of flog — backup restore errors not in app logs
- **File:** `app/settings/advanced/RestoreScreen.kt`  ·  **fix risk:** low
- **Verified:** Both cited lines exist exactly as claimed: RestoreScreen.kt:223 `error.printStackTrace()` inside `restoreSelectedSection { ... }.onFailure`, and :376 `e.printStackTrace()` in the outer `startRestore()` catch. Both are genuine data-mutation paths (FlorisPreferenceStore.import, srcDir.copyRecursively after deleteContentsRecursively in Erase mode, clipboardManager.restoreHistory + clipboardFilesDao().insert). The strongest evidence the finding is real: the sibling BackupScreen.kt in the SAME directory (lines 191, 316) already does `flogError { error.stackTraceToString() }` for its failure path — so RestoreScreen is an inconsistency against the codebase's own established idiom, and `flogError` is a real, imported symbol (dev.patrickgold.florisboard.lib.devtools.flogError). HOWEVER the finding's severity reasoning is overstated and partly wrong. Reading Flog.kt: flogError logs only when checkShouldFlog() is true, which requires isFloggingEnabled (debug instrumentation, gated off in release). The only implemented output is OUTPUT_CONSOLE -> Log.e (logcat); fileLog() is a no-op TODO stub. So (a) in a release build flogError likely emits NOTHING while printStackTrace at least reaches logcat via System.err, and (b) there is NO log-file capture for a user to attach to a bug report under either approach. The finding's headline ('errors not in app logs', 'no structured log for a release bug report') therefore does not hold — this is a code-consistency / minor-UX issue, not a high-severity data/error-handling defect. The blank-toast concern (localizedMessage null on NPE/IO) is a legitimate small UX nit worth the optional null-fallback. No data loss results from the logging choice itself.
- **Fix:** Quality/consistency fix (low severity). Match BackupScreen's idiom. Line 223: replace `error.printStackTrace()` with `flogError { error.stackTraceToString() }`. Line 376: replace `e.printStackTrace()` with `flogError { e.stackTraceToString() }`. Add `import dev.patrickgold.florisboard.lib.devtools.flogError`. Optionally address blank toasts/cards: in markFailed() (line 205) use `error.localizedMessage ?: error::class.simpleName` and at line 378 `lastRestoreErrorMessage = e.localizedMessage ?: e::class.simpleName`. Do NOT frame this as fixing release-build diagnosability — flogError is gated off in release and fileLog is a stub, so it produces no persisted log; printStackTrace already reaches logcat. The real value is codebase consistency plus the optional non-null error message.
