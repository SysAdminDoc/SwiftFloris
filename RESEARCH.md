# Research — SwiftFloris

Date: 2026-08-11 — replaces all prior research (previous pass: 2026-08-10).

## Executive Summary

SwiftFloris v1.9.59 (versionCode 2108) is a mature, privacy-first Android IME: 1,034 Kotlin files across `:app` and five `lib/*` modules, 359 `*Test.kt` files, 2,202 passing JVM tests (`:app:testDebugUnitTest`, 3m27s, verified 2026-08-11), 25 local gate scripts plus 13 self-tests, no `INTERNET` permission, no accounts, no CI. All ten opportunities from the 2026-08-10 pass shipped in the 16 commits to v1.9.59 and `ROADMAP.md` is drained to one P3 item. Upstream FlorisBoard is effectively stalled — two commits to `main` since 2026-05-01, last stable release 2025-11-28 — so the fork now leads its own lineage.

The highest-value direction is no longer "more verification". It is **making the verification mean what the documentation says it means.** The repo has a strong verification culture and no CI behind it — and this pass found that several of its gates cannot fail. One is broken outright, several are scoped by hand-written lists that certify whatever they omit, two are red at HEAD and were not run before v1.9.59 was cut, and a class of tests asserts on production *source text* rather than production behaviour. The docs then quote these gates as general guarantees. Unless marked otherwise, findings are **Verified** against the working tree at commit `8e7c4e6eb`; the two most severe were reproduced by hand.

Top opportunities, in priority order:

1. **The release vulnerability gate cannot block anything.** `scripts/osv-release-gate.py:58-76` parses the CVSS *vector string* as if it were the score: `"CVSS:3.1/AV:N/…/A:H"` → `split("/")[0].split(":")[-1]` → `3.1` → `LOW`. Reproduced. Every CVSS v3 advisory grades LOW, every v4 grades MEDIUM, and `BLOCKING_SEVERITIES = {"HIGH","CRITICAL"}` is unreachable. It is the only vulnerability gate in the release flow and `docs/SECURITY.md:92-93` claims it blocks.
2. **Incognito does not suppress inline ghost text.** `ime/nlp/NlpManager.kt:249-259` captures `isPrivateSession` (the user-toggled incognito) into the privacy snapshot, then `:347-353` passes only `isEditorSensitive` into `buildGhostTextCandidate`, which gates solely on that. `isEditorSensitive` reads `inputType`/`imeOptions` and cannot see a user-forced or per-app incognito. With `heuristicSmartCompose` enabled (default off), previously-learned personal words render as ghost text while incognito is on. The sibling path gets it right — `LatinLanguageProvider` returns empty on `isPrivateSession`.
3. `docs/THREAT_MODEL.md:142-145` guarantees the system user dictionary is never written; `SystemUserDictionaryDatabase` ships `insert`/`update`/`delete` against `UserDictionary.Words.CONTENT_URI` and the Settings editor routes to them. Any app holding `READ_USER_DICTIONARY` can then read those words — the exact leak `PersonalDictionaryIsolationTest` exists to prevent on the learning path.
4. **Two gates are red at HEAD and v1.9.59 shipped anyway.** `scripts/check-release-front-door.sh` fails with 3 errors (no `v1.9.59` tag locally or on origin, no GitHub Release) and `scripts/check-repo-hygiene.sh` fails on a stale allowlist entry. Both are wired into `release-evidence.ps1` with `AllowedExitCodes = @(0)`, which proves the runner was not executed for this release. Tags stop at `v1.9.56` while `fdroid/io.github.sysadmindoc.swiftfloris.yml:25` pins `commit: v1.9.59`, so the F-Droid recipe cannot resolve either.
5. The APK-level no-network gates are still five-name denylists (`app/build.gradle.kts:309-315`, `scripts/verify-addon-apk.sh:42-46`) while the runtime enrolment gate became an allowlist in v1.9.59 — and `NoNetworkPermissionPolicy.kt:29-43` documents exactly why the denylist was wrong. The two halves of the same promise now disagree.
6. ~900 LOC of smart-compose/MCP router stack has no production caller, so the privacy audit log has readers and no writer — a user reads an empty log as "no AI invocation occurred" — while `McpServiceLifecycle` still binds every discovered third-party daemon for a dispatch path that cannot fire.
7. `Roadmap_Blocked.md`'s entire hardware section (11 items) rests on "`adb devices -l` is empty". A device is attached right now (`R5CY34G070L`, SM-S938B, Android 16 / SDK 36) with the debug build already installed. Nine of eleven blockers have cleared, and six tracked public JSON files publish that device's hardware serial.
8. Stylus handwriting is fully implemented in `FlorisImeService` behind a shipped Settings toggle, but `res/xml/method.xml` omits `android:supportsStylusHandwriting`, which AOSP defaults to `false` — the platform can never invoke it. `android:supportsInlineSuggestionsWithTouchExploration` is likewise absent, so inline autofill is suppressed for TalkBack users.
9. Three shipped themes fail WCAG AA on the key-hint glyph (3.84 / 4.08 / 4.37:1, computed); `ThemeContrastTest` checks 10 of 98 selectors and `key-hint` is not among them. Cold start separately flashes *"No themes available … If this stays empty, reinstall SwiftFloris"* because three screens render their empty state before the data flow emits.
10. Glide typing dies whenever a second finger touches the keyboard (`GlideTypingGesture.kt:66-68`) — dual-thumb swipe is the single most-repeated must-have in the highest-traffic 2026 keyboard thread on Hacker News. And 2,541 strings ship while locales carry 830–999 (33–39%), with no fork-added string in any locale.

## Product Map

- **Core workflows:** enable the IME and type/correct/glide; emoji, stickers, snippets, clipboard history with search and pinning; multilingual subtypes, hardware layouts, CJK and transliteration; themes, per-app profiles, privacy posture, addons and the MCP bridge; backup/restore (manual + scheduled, encrypted), dictionary migration, diagnostics.
- **User personas:** privacy-conscious Gboard/SwiftKey migrants; multilingual and minority-script typists; offline users; hardware-keyboard, accessibility, Tasker and addon users; F-Droid/Obtainium reviewers.
- **Platforms and distribution:** Android 8.0+ (`minSdk 26`), `targetSdk 36`, `compileSdk 37`; local builds plus GitHub Releases and Obtainium, F-Droid recipe prepared; Apache-2.0.
- **Key integrations and data flows:** Room/SQLCipher stores, Tink/Android Keystore, SAF and share-sheet import/export, signed addon APKs, external voice IMEs, exported Tasker plugin, local Binder/AIDL MCP daemons, and — undocumented in the threat model — the platform `UserDictionary` content provider.
- **Contract-only subsystems (no runtime ships):** handwriting recognition (`ime/handwriting/StrokeRecognizer.kt:29-30`), inline translation (`ime/translate/InlineTranslator.kt:32`), local voice recognition (`VoiceRecognitionEngineSelection.kt:50-51`). Smart compose is the exception — `HeuristicSmartComposeProvider` is a real shipping provider. The `addons/` tree holds one sample module (dictionary pack); no runtime addon exists for any of the five `REGISTER_*_RUNTIME` actions declared in the manifest.

## Security, Privacy, and Reliability

- **Verified by reproduction — the OSV release gate fails open.** `scripts/osv-release-gate.py:58-76` reads `severity[].score`, which for `CVSS_V3`/`CVSS_V4` is the vector string, and computes `float(score_str.split("/")[0].split(":")[-1])`. For `CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H` — a 9.8 — that yields `3.1`, which maps to `LOW`. v4 vectors yield `4.0` → `MEDIUM`. Because the loop returns inside the `if`, the `database_specific.severity` fallback at `:73` is unreachable once any CVSS entry is present, and `"UNKNOWN"` is also non-blocking. With `BLOCKING_SEVERITIES = {"HIGH", "CRITICAL"}` (`:36`), **no advisory can ever block a release**. This is the only vulnerability gate in `scripts/release-evidence.ps1:287-290`, there is no CI behind it, and `docs/SECURITY.md:92-93` states that it blocks.
- **Verified — user-toggled incognito does not gate ghost text.** `ime/nlp/NlpManager.kt:249-259` builds the request snapshot with both `isPrivateSession = keyboardManager.activeState.isIncognitoMode` and `isEditorSensitive`. `:347-353` forwards only `isEditorSensitive` to `buildGhostTextCandidate`, and `:369-373` gates on that alone. `SensitiveFieldGuard.isSensitive` derives from `inputType`/`imeOptions`, so it covers a field that declares `IME_FLAG_NO_PERSONALIZED_LEARNING` but not the user's own incognito toggle or a per-app incognito profile (`SuggestionPrivacyPolicy.kt:48-59`). `FlorisApplication.kt:113-117` registers `HeuristicSmartComposeProvider` in release builds and it reads `PersonalTrigramStore`/`PersonalBigramStore` (`HeuristicSmartComposeProvider.kt:92-105`), so with `correction__heuristic_smart_compose` on — default `false`, `CorrectionPrefs.kt:116`, which bounds the blast radius — learned personal words surface as ghost text in an ordinary field while incognito is active. The word-suggestion path handles this correctly (`LatinLanguageProvider` returns empty on `isPrivateSession`), and `README.md:58` advertises "request-scoped privacy snapshots for incognito". A stale comment at `FlorisApplication.kt:134` ("leave the default no-op provider in place") makes the release-build registration easy to miss.
- **Verified by execution — two release gates are red at HEAD.** `bash scripts/check-release-front-door.sh` → `release-front-door: FAIL (3 error(s))`: `gradle.properties` and README claim v1.9.59, the newest local tag is v1.9.56, and neither an origin tag nor a GitHub Release exists. `bash scripts/check-repo-hygiene.sh` → error: `scripts/source-stub-hygiene-allowlist.tsv:2` still allowlists a `// FIXME: This is a workaround!` needle in `lib/android/build.gradle.kts` that v1.9.59 removed. Both are invoked by `scripts/release-evidence.ps1:252-253` with `AllowedExitCodes = @(0)` and a `throw` on failure, so the evidence runner demonstrably did not complete for this release. The stale-entry detector that caught the second one (`check-repo-hygiene.sh:100-103`) is the only place in the repo that validates an allowlist for vestigial entries — good design, not being run.
- **Verified — the threat model guarantees a write path that ships.** `docs/THREAT_MODEL.md:142-145`: *"`enableSystemUserDictionary` is opt-in; even when on, it only **reads** from the system provider, never writes."* `ime/dictionary/UserDictionary.kt:557-566` (`insert` → `resolver.insert(UserDictionary.Words.CONTENT_URI, …)`), `:569-577` (`update`), `:580-582` (`delete`) are live implementations inside `SystemUserDictionaryDatabase`, and `app/settings/dictionary/UserDictionaryScreen.kt:233` routes `UserDictionaryType.SYSTEM` to that DAO, reaching them at `:980`, `:982`, `:1026`. The *automatic learning* path is genuinely isolated — that is what `PersonalDictionaryIsolationTest.kt:30,64` protects, and its comment states the stakes: any app with `READ_USER_DICTIONARY` can enumerate what lands there. The manual editor bypasses the invariant, and the app declares no `WRITE_USER_DICTIONARY`, so either the writes leak user words to every IME on the device or they fail silently. Both outcomes are undocumented.
- **Verified — the APK-level no-network gate is a five-entry denylist.** `app/build.gradle.kts:309-315` lists `INTERNET`, `ACCESS_NETWORK_STATE`, `ACCESS_WIFI_STATE`, `CHANGE_NETWORK_STATE`, `CHANGE_WIFI_STATE` and applies them to both source and merged manifests. `scripts/verify-addon-apk.sh:42-46` uses the identical five. Meanwhile `ime/security/NoNetworkPermissionPolicy.kt:73-81` became a seven-entry *allowlist* in v1.9.59 precisely because `SEND_SMS`, Bluetooth, nearby-devices, storage and Android 17's `ACCESS_LOCAL_NETWORK` move data without `INTERNET`. `scripts/check-trust-capabilities.py:98` pins the app's permission set exactly — but only for `app/src/main/AndroidManifest.xml`. Nothing checks the merged manifest or the built APK against an allowlist, so a dependency AAR merging in any non-network exfil permission ships unnoticed, and a third-party addon author who self-certifies with `verify-addon-apk.sh` gets a PASS on an APK the IME will reject at enrolment.
- **Verified — release tags are missing and the F-Droid recipe is unresolvable.** `git tag | sort -V | tail` ends at `v1.9.56`; v1.9.57, v1.9.58 and v1.9.59 are untagged commits. `fdroid/io.github.sysadmindoc.swiftfloris.yml:25` pins `commit: v1.9.59`. F-Droid's builder resolves the tag literally, so the prepared recipe would fail on submission — which is the item `Roadmap_Blocked.md:135-139` treats as awaiting only a GitLab MR.
- **Verified — a hardware serial is published in the repo.** All six `docs/benchmark-results/baseline-2026-05-18-*.json` are `git ls-files`-tracked and embed `"serial": "R5CY34G070L"` alongside manufacturer/model/device. For a keyboard whose entire positioning is "no identifiers leave the device", a maintainer's device serial in a public repo is an avoidable contradiction. No doc claims otherwise, so this is an unflagged leak rather than a false claim.

Both backup XML rule sets are include-lists, so new data files fail closed — the opposite of the classic bug (the `personal_bigrams`/`personal_trigrams` `<exclude>` paths do not match the real `personal_bigrams_<localeTag>.tsv` filenames, but nothing includes them, so this is decorative rather than a leak). `ZipUtils.unzip` is thoroughly hardened — entry-count cap, pre-canonical name guard, canonical-prefix zip-slip check, per-entry and per-archive byte caps (`lib/io/ZipUtils.kt:53-63,240-330`); its only defect is a KDoc claim that a security abort leaves no partial extraction, which nothing enforces (contained to a temp workspace in every caller). Zero `@Ignore`/`@Disabled` tests, zero `TODO()`/`NotImplementedError` stubs, zero empty `catch` blocks, zero `FIXME`, no lint baseline and no lint suppression debt, 20 inherited low-priority `TODO`s, and only two files over 1,500 lines (`TextKeyboardLayout.kt` 1,659; `KeyboardManager.kt` 1,540).

## Architecture Assessment

- **The smart-compose / MCP router stack is built, tested and unreachable.** `ime/smartcompose/SmartComposeRouter.kt`, `SmartComposeCache.kt`, `SmartComposeContextWindow.kt`, `SmartComposeResultFilter.kt`, `OptInAddonDispatcher.kt`, `RewriteRouter.kt` and `NlpAddonHub.kt` are constructed only in `app/src/test`. The shipping path calls `SmartComposeProviderRegistry.active.predictNextTokensAsync(...)` directly (`NlpManager.kt:383-390`), bypassing the router's context truncation, cache, result filter **and `AddonInvocationAudit.record(...)`**. `PrivacyAuditDisplay.kt` and `PrivacyAuditExportPolicy.kt` are the audit log's only production references — readers with no writer — so `PrivacyAuditScreen` will always show an empty smart-compose log, which a user reads as "no AI invocation occurred". Meanwhile `FlorisImeService.kt:428-437` → `McpServiceLifecycle.kt:56-71` still binds every discovered daemon, and the only caller of `McpDispatchRouter.dispatch` is the uncalled `NlpAddonHub`: live `ServiceConnection`s to arbitrary third-party APKs for a dispatch path that cannot fire. `README.md:337` claims the smart-compose path reaches those tools. Whichever dispatcher is wired first also decides whether `DisabledDaemonSet`/`DisabledToolSet` and the `McpPrefs` toggles ever gate anything — `OptInAddonDispatcher.kt:80-99` calls `mcpClient.callTool` directly while its own KDoc calls itself "the load-bearing privacy-enforcement seam".
- **Three more unreachable subsystems, two of them behind live UI.** `AdvancedSpellingProvider`/`AdvancedPredictionProvider` (`ime/nlp/advanced/AdvancedProviders.kt:194-394`, ~200 LOC) have provider IDs that appear nowhere but their own declarations, and ship three dead assets under `assets/lm/`; two latent bugs sit inside them (`:333-335` `removeSuggestion` returns `true` without removing; `:290-320` accepts `isPrivateSession` and `allowPossiblyOffensive` and ignores both while LRU-caching raw `textBeforeSelection`). `InlineTranslatorRegistry` is never populated but `QuickAction.kt:99-158` ships a live `TranslateSelection` smartbar action that can only toast "unavailable". `StrokeRecognizerRegistry` is likewise empty behind the stylus toggle. `KenLmBinaryHeader.kt:121-123` parses `probingMultiplier`/`pointerBhiksha` and discards them — the trie body parser is unimplemented.
- **Doc integrity is the root cause, and its gate is scoped away from it.** `scripts/check-live-doc-integrity.py` reports `OK (11 files checked)` while 23 of 27 `docs/*.md` files are untracked (absent from a clean clone) and the five planning docs are explicitly excluded. Downstream: 63 dangling `ROADMAP §N` / `Next-N.N` / `matrix #N` references across 15 docs against an 18-line `ROADMAP.md` with no numbered sections; `CHANGELOG.md` has no v1.8.x sections, so 31 v1.8.x attributions in `THREAT_MODEL.md` alone are unresolvable; eight `.github/workflows/*.yml` files are cited across two docs and no `workflows/` directory exists. Fixing the gate's scope is worth more than fixing any individual doc.
- **The blocked roadmap has drifted from the tree.** Beyond the hardware section: "Addon developer trust kit" is blocked on needing a buildable addon APK that is a first-class Gradle module built and validated on every release run (`settings.gradle.kts:47`, `release-evidence.ps1:262-272`); "Expand instrumented coverage" describes a test that exists (`ImeEndToEndSmokeTest.kt:64`); "Local voice recognizer runtime" is blocked on size and licence review that `VoiceModelCatalog.kt:31-32,46-68,150` already carries as typed fields for nine models; "Sync transport — no protocol selected" contradicts `SyncChannel.kt:22-44,51,76`, which selects Syncthing/local-folder and explains why the transport is deliberately not the IME's problem; "CJK production data" describes a "skeleton" that ships 235,847 rows; the NLnet watch item's June 2026 deadline lapsed ten weeks ago. The VNI-composer analysis at `Roadmap_Blocked.md:30-42` is exact — 2,866 Telex rules, 913 pure-ASCII undo rules, 60 `z`-key rules — and should not be redone.
- **Verification runs at SDK 35.** Every Robolectric test is `@Config(sdk = [35])`, including the Roborazzi preview generator (`app/build.gradle.kts:265`). Robolectric 4.16.1 has no SDK 37 shadows (4.17-beta-2 is the first that does), and `buildTools` is pinned to 36.0.0 against `compileSdk 37`. The platform *policies* are unit-tested at the value 37, which is sound design, but nothing executes against an API 36/37 runtime. With a device now attached, instrumented coverage is the cheaper answer than chasing a Robolectric beta.
- **Empty states race their own data.** `theme/ThemeManagerScreen.kt:111-118`, `ext/ExtensionListScreen.kt:164-178` and `settings/addons/AddonsSettingsScreen.kt:232-239,249-257` render "nothing here" before their flows emit. The theme case tells a first-run user to reinstall the app. `AddonsSettingsScreen` renders the progress card *and* two empty states simultaneously during the first scan. Separately, `dictionary/UserDictionaryScreen.kt:881-903`'s per-locale empty state is unreachable because `loadUiSnapshot` (`:251-273`) nulls `currentLocale` when a locale returns zero words, so deleting the last word bounces the user out with no explanation and two shipped strings are dead.
- **There is no undo infrastructure.** Zero `Snackbar`/`SnackbarHost` in `app/` or `lib/`; feedback is 62 `Toast.makeText` calls. Against the project's stated preference for immediate action plus undo, the surface splits into 11 confirmation dialogs and 8 deletions with neither confirmation nor undo — including single clipboard-entry delete (`ime/clipboard/ClipboardInputLayout.kt:786-792`), which is silent, and per-app profile delete (`privacy/PerAppKeyboardProfileScreen.kt:356-360`), a destructive action in a dialog's *dismiss* slot. One `SnackbarHost` fixes the whole category. There is also no "reset all settings" anywhere.
- **Accessibility: shared widgets are 4 dp under the Android floor.** `lib/compose/FlorisButtons.kt:69,106,143,206`, `FlorisButtonBar.kt:84,107`, `FlorisChip.kt:57` and `FlorisCards.kt:516` standardise on `44.dp` — the iOS number — while `FlorisButtons.kt:179,215` correctly use `minimumInteractiveComponentSize()`. The keyboard surface itself is fine (`ImeWindowSpec.kt:95` coerces to a 48 dp floor). `docs/ACCESSIBILITY.md` then overstates conformance in six places: it claims `announceForAccessibility` is never called (`KeyboardManager.kt:602-605` calls it), that `TRANSITION_ANIMATION_SCALE` is respected (zero occurrences), that a non-existent Compose API `LocalConfiguration.current.reduceMotion` is consulted (the real helper is `rememberReducedMotion()` at `lib/compose/ReducedMotion.kt:31`, with no call site under `ime/smartbar/`), that Snygg has a per-element contrast warning in the theme editor (it has none), and that `TouchTargetWcagTest` enforces 48 dp app-wide (it is height arithmetic over keyboard rows on one synthetic device). A doc that overstates conformance is worse than no doc.
- **Two platform attributes are missing from a 20-line file.** `res/xml/method.xml` declares `supportsInlineSuggestions` and `supportsSwitchingToNextInputMethod` but neither `android:supportsStylusHandwriting` nor `android:supportsInlineSuggestionsWithTouchExploration`. Both default to `false` in AOSP (`InputMethodInfo.java`). The first makes `onPrepareStylusHandwriting`/`onStartStylusHandwriting`/`onStylusHandwritingMotionEvent`/`onFinishStylusHandwriting` (`FlorisImeService.kt:601-680`) and the `keyboard__stylus_handwriting_enabled` toggle unreachable; the second suppresses inline autofill for every TalkBack user.
- **Localisation is structurally broken, not merely incomplete.** 2,541 source strings; `values-de` 869, `values-fr` 872, `values-ar` 830, `values-zh-rCN` 999. v1.9.59 fixed the *mapping* (all 43 locales now have a route and `scripts/check-locale-coverage.py` gates it), but `crowdin.yml:1-2` still names `FSEC_CROWDIN_PROJECT_ID`/`FSEC_CROWDIN_PERSONAL_TOKEN` — upstream FlorisBoard's project — and nothing in the tree consumes the file. Consequently no fork-added string (`settings__mcp__*`, `settings__sync__*`, `settings__migration_assistant__*`, `settings__search__*`, snippets, typing stats, per-app profiles) has ever been submitted for translation, and Arabic and Hebrew users get a mostly-English RTL settings app. There is also no `android:localeConfig` and no in-app language picker, so the app's UI language cannot be set independently of the system on Android 13+.
- **Migration has two dead ends.** `dictionary/MigrationAssistantScreen.kt:95-100` is titled "SwiftFloris encrypted backup (.sfexp)" and navigates to `Routes.Settings.Restore`, which handles `.sfbak`/ZIP archives and has no dictionary path — `.sfexp` is produced and consumed only inside `UserDictionaryScreen.kt:113,1148-1165`. And `ime/dictionary/DictionaryImporter.kt:183-192` throws on `.db`/`.sqlite` entries with a message directing the user to an "Import .flbackup path" that exists nowhere. Separately, the personal dictionary — everything a SwiftKey/Gboard migrant brings — is `SensitiveExcluded` from backups (`BackupDataInventory.kt:201-214`) and the coverage notice never says so; and import-on-collision overwrites `freq`/`shortcut` irrecoverably (`PersonalDictionaryImportBatch.kt:102-113,146-150`) while the summary reports only "Updated N existing words".
- **Settings search covers 27% of settings and cannot detect its own gaps.** `SettingsSearchIndex.kt:119-238` is a literal list of 106 entries (81 preferences) against ~300 rendered `Preference(...)` composables; Input Feedback 0/16, Addons 0/8, MCP 0/9, Gestures 7/28. Deep links render a card at the top of the target screen rather than scrolling to the row, and search is reachable only from Home. Generating the index — or failing a test when a `Preference` has no entry — is the structural fix.
- **Glide is single-pointer, and gives up when a second finger lands.** `GlideTypingGesture.kt:66-68` returns `false` on `ACTION_POINTER_DOWN` if a pointer is already tracked, and its `ACTION_MOVE` branch compares against `event.getPointerId(event.actionIndex)`, which is always index 0 for a move. Two-thumb swipe is impossible, and a glide started while another finger rests on the keyboard never registers movement.
- **A large-clipboard stall is untested against an encrypted store.** FlorisBoard reports a clipboard-open freeze (#3117) and a crash on over-long clipboard text (PR #3303); HeliBoard reproduces a multi-second stall at ~120 KiB of URLs (#2697). SwiftFloris bounds retention at 64 KiB UTF-8 (`ime/clipboard/ClipboardTextRetentionPolicy.kt:32`) and routes larger live clips to direct paste, which is the right design — but the history store is SQLCipher-encrypted (`ClipboardHistoryEncryption.kt:23,45-48`) and search/filter runs over decrypted rows, so encryption makes this defect class worse rather than better, and no fixture replays it.
- **Unicode 18.0 ships 2026-09-16** with nine new emoji, against bundled data generated from CLDR 48 / Emoji 17.0. The regeneration path and the version header are now correct (v1.9.59), so this is a scheduled data refresh — but `EmojiDataVersion` (`ime/media/emoji/EmojiData.kt:30-33`) still has no production consumer, only `EmojiDataVersionTest`, so nothing would notice stale data at runtime.
- **No hinge awareness.** Only `androidx.window:window-core` is on the classpath, used solely for `WindowSizeClass` (`ime/window/ImeFormFactor.kt:23-24`). Split-keyboard geometry is size-class-driven; there is no `WindowInfoTracker`/`FoldingFeature` consumer, so the split gutter never aligns to a physical hinge.
- **Dependency currency.** Current and correct: Kotlin 2.4.10, AGP 9.3.0, Room 2.8.4, Tink 1.23.0, SQLCipher 4.17.0, Compose BOM 2026.06.00, kotlinx-serialization 1.11.0, coroutines 1.11.0, emoji2 1.6.0, autofill 1.3.0, ZXing 3.5.4. Behind (verified against Maven metadata on 2026-08-11): Gradle 9.6.1 → **9.7.0**, `androidx-core` 1.18.0 → **1.19.0**, `androidx-sqlite` 2.6.2 → **2.7.0**, Coil 3.4.0 → **3.5.0**, Roborazzi 1.70.0 → **1.71.0**, Kotest 6.2.3 → **6.2.4**, KSP 2.3.9 → **2.3.11**, `buildTools` 36.0.0 → **37.0.0**, Robolectric 4.16.1 → **4.17-beta-2** (first with SDK 37). `androidx-core` 1.19.0 carries `TextAttributeCompat`, the compat backport of the API 37 suggestion-selected attribute SwiftFloris already writes behind an API-37 guard.
- **Category coverage.** Security, privacy, accessibility, i18n, testing, docs, distribution, migration and UX all produced concrete work. Observability produced one item (in-app bug reporting): the crash path is genuinely good — handler, capped store, notification, copyable dialog with build metadata — but `AboutScreen` has no issue-tracker link, the app cannot supply the device/Android-version/install-source fields its own `.github/ISSUE_TEMPLATE/bug_report.yml:34-65` demands, and neither the crash dialog nor the debug-log export offers a share intent. Multi-user remains intentionally excluded; work-profile/cross-profile behaviour (FUTO #2168) is unexamined in this tree but is device-testable now.

## Rejected Ideas

- Kotlin 2.4.20-Beta2 for CVE-2026-53914 — shipping a beta compiler under a production keyboard to close a local, high-privilege attack on a build cache this repo does not share. Already tracked in `Roadmap_Blocked.md`; the premise is now stale (it says "bump 2.4.0", the build is on 2.4.10) but the conclusion holds.
- Migrating off `SHOW_IMPLICIT`/`HIDE_IMPLICIT_ONLY`/`HIDE_NOT_ALWAYS`/`SHOW_EXPLICIT` (deprecated in API 37) — none are used; the single `showSoftInputFromInputMethod` call passes `0` (`FlorisImeService.kt:192`).
- Privacy Sandbox on Android adoption — retired by Google on 2025-10-17; remove from consideration permanently.
- Compose BOM 2026.06.00 → 2026.06.01 — resolves to identical library versions; pure churn. (Unchanged from the 2026-08-10 pass.)
- A compatibility emoji font — `FlorisEmojiCompat` already degrades via `Paint.hasGlyph`. (Unchanged.)
- Rewriting Telex as an algorithm (FlorisBoard #3316) — already table-driven. (Unchanged.)
- Per-app incognito override (HeliBoard #2719), spacebar swipe-to-switch-language (FUTO v0.1.30), split/one-handed for foldables (AnySoftKeyboard #4788), R8/resource shrinking (AnySoftKeyboard #4838), key-popup vs autofill z-order (HeliBoard #2721), shift-lost-during-glide (#2720), emoji-search-state persistence (#2698), spacebar-swipe crash (#2707), emoji suggestion beside the word (HeliBoard #2704), Page Up/Down as bindable actions (FUTO #2155) — all already shipped; see the 2026-08-10 pass and v1.9.59 for the specific call sites.
- Importing Gboard/SwiftKey personal dictionaries (FUTO #2203) — already shipped via `DictionaryImporter.kt:86-372`; what remains are the two broken migration routes listed above, not the importer.
- Glide auto-disable on low-RAM devices (AnySoftKeyboard #4840) — shipped in v1.9.57.
- Custom layout editor (FlorisBoard #196) — already shipped (`app/settings/keyboard/CustomLayoutEditorRepository.kt`, plus Keyboard3/KLC/Keyman import).
- A desktop web theme editor (FUTO v0.1.30) — genuinely attractive, but it needs hosting, a second toolchain and a Snygg-schema publication story for a feature the in-app editor already covers for the common case. Reconsider only after the theme editor gains contrast validation, which is the actual quality gap.
- Guarding against cross-app KeyEvent injection, cloud AI, account sync, cloud clipboard, telemetry, an online addon store, multi-user profiles, bundled GPL keyboard code — unchanged rejections; reasoning in prior passes still holds.

## Open Questions

- Should the system user dictionary be writable at all? Making `SystemUserDictionaryDatabase` read-only matches the threat model and closes the `READ_USER_DICTIONARY` leak, but removes the only way to edit words that other IMEs on the device also use. The alternative — keep the writes and document them with an explicit in-UI warning — is a product decision about who SwiftFloris's system-dictionary users are, and nothing in the tree records the original intent.
- Is the Crowdin project still live and owned by this fork? `crowdin.yml` still names FlorisBoard's `FSEC_*` env vars. If the account is gone, the correct fix is to delete the config and document a PR-based translation path; if a fork project can be created, the 1,600-string gap becomes a submission rather than a rewrite. (Carried from 2026-08-10; the locale *mapping* was fixed in v1.9.59, the ownership question was not.)
